# v6.0.0 pre-release audit report

[**Back to README**](../../README.md) · See also: [CHANGELOG](../../CHANGELOG.md) · [ADR001V03](../adr/ADR001V03-concurrency-model-for-ring-buffer-manager-scale-up-and-down.md) · [ADR003V03](../adr/ADR003V03-median-sample-autoscaling-algorithm.md) · [ADR007V03](../adr/ADR007V03-redesign-of-the-public-fluent-api-surface.md)

This is a factual record of the hardening process the `v6` branch went through before shipping as v6.0.0: what was reviewed, how, what it found, and what shipped as a result. It is release evidence, not a tutorial — it exists so a future maintainer (or auditor) can see why v6.0.0 is trusted, without having to re-derive it from commit history.

## Scope

The audit covered the full `v6` branch surface built on [ADR001V03](../adr/ADR001V03-concurrency-model-for-ring-buffer-manager-scale-up-and-down.md) (concurrency model), [ADR003V03](../adr/ADR003V03-median-sample-autoscaling-algorithm.md) (autoscale algorithm), and [ADR007V03](../adr/ADR007V03-redesign-of-the-public-fluent-api-surface.md) (public API surface) — the engine, its telemetry, its public documentation, and its test suite. It did not re-litigate those three ADRs' own design decisions; it checked whether the implementation, its failure behavior, and its documentation actually match what they claim.

## Method

The audit ran as a series of independent review passes ("fronts"), organized into numbered rounds, rather than as one open-ended pass. Six fronts were established at the start, each owned by its own independent reviewer with no visibility into the others' findings within a round:

| Front | What it checks |
|---|---|
| Estabilidade | Correctness under concurrency and shared state — races, invariant violations, unsafe assumptions about ordering. |
| Resiliência | Behavior under failure — retries, timeouts, shutdown, degraded modes. |
| Usabilidade | Public API ergonomics and whether documentation actually matches the shipped code. |
| Complexidade | Algorithmic complexity and allocation profile of hot paths, static analysis only. |
| Desempenho | Empirical performance — real benchmark numbers before/after, never a claimed regression or gain without a measurement. |
| Observabilidade | Whether metrics, logs, and traces actually reflect what the system is doing, not what it's assumed to be doing. |

**Per round:** each active front ran as a genuinely separate pass (no shared context between fronts), read the current code and docs fresh, and reported findings independently. Findings were then merged without silently reconciling disagreement between fronts. Every finding was classified Crítico / Alto / Médio / Baixo.

**Fixing:** a finding with one unambiguous correct repair was fixed directly, using red/green verification (a failing test proving the defect for the right reason, then the fix, then a full green run — [`FloorGuardDecisionTests.cs`](../../src/RingBufferPlus.Tests/FloorGuardDecisionTests.cs) and the `AcquireAsync_AfterWarmupFailureIsCached_...` family in [`RingBufferObservabilityTests.cs`](../../src/RingBufferPlus.Tests/RingBufferObservabilityTests.cs) are representative examples). A finding whose fix carried a real trade-off (a behavior change, a measurable cost, more than one defensible answer) was never decided unilaterally — it went back to the maintainer with the options and their costs spelled out, and only implemented after an explicit choice.

**Corroboration:** a front's own suspicion of a bug was not treated as confirmed until reproduced empirically — several plausible-sounding theories raised during the audit (an `Activity.Current` parent-chaining leak across scale operations, a suspected missing log in `SwitchToAsync`'s unlocked path) were tested directly against the real engine and refuted; each refutation was converted into a permanent regression-guard test rather than discarded, so the audit's own negative results stay checkable. Where a fix pattern was found once, the rest of the codebase was searched for sibling occurrences before considering that class of defect closed (e.g. the `acquire.*`/`scale.*` metric-vs-trace tag asymmetry, found and fixed independently on each signal across three separate rounds once a full search confirmed no other occurrence remained).

**Convergence:** a front was considered formally converged once it produced zero Crítico/Alto findings for two consecutive rounds — at which point it was taken out of full rotation (reduced to a targeted check, or dropped entirely) rather than kept running at unchanged cost indefinitely. This is what let the audit scale down over its own lifetime instead of running all six fronts at full weight for every round regardless of what they were still finding.

**Stopping:** the audit ran for as many rounds as the findings justified, not a fixed count. The stop criterion for the final round was set *before* that round ran, not decided after seeing its results: if the two fronts still finding real items (usabilidade, observabilidade) came back with only residual/self-referential findings, the audit would close.

Full per-finding detail for all 12 rounds lived in the audit's working files (`TODO/relatorio-auditoria-v6.md`, `TODO/plano-de-acao-v6.md`, `TODO/acompanhamento-convergencia-v6.md`) for the duration of the audit; per the project's own convention for this kind of ephemeral tracking, those are not retained as standing documentation once the audit concludes — this report and the CHANGELOG are its durable record.

### Convergence achieved

- **Estabilidade** and **Resiliência** — formally converged at Round 6 (2 consecutive clean rounds), reduced out of full rotation from Round 7 onward.
- **Complexidade** — formally converged at Round 10 (2 consecutive clean rounds), removed from rotation from Round 11 onward.
- **Desempenho** — never intended to "converge": redefined at Round 9 as a permanent regression-verification function tied to actual code changes (it measures whatever changed that round, or reports there was nothing to measure), not a front that must find progressively less to be considered done.
- **Usabilidade** and **Observabilidade** — never reached 2 consecutive clean rounds, but their findings' severity and novelty strictly declined: no genuinely new class of behavior bug from either front after Round 10, only propagation of already-made decisions to a sibling file, or characterization precision on an already-mapped edge case. This plateau, combined with the pre-committed stop criterion, is why the audit closed at Round 12 rather than continuing to chase a formal convergence threshold neither front was trending toward triggering.

### Notable defects found and fixed

- **Warmup-failure telemetry blackout** (Round 7–8): every implicit `AcquireAsync` call after an initial warmup failure was cached (`Lazy<Task>`, per [ADR011](../adr/ADR011V01-retry-path-for-a-failed-warmup-async-instead-of-a-permanently-broken-instance.md)) rethrew before any Activity or metric was ever recorded — a buffer could fail 100% of its calls with zero telemetry. Fixed by recording an `acquire.duration` row and Activity on that path too, disambiguated from an ordinary shutdown race by a new `acquire.warmup_failed` tag.
- **Floor-guard log storm** (Round 10): the "below minimum capacity" error re-fired on every single retry evaluation once the grace window elapsed, at whatever cadence the caller happened to retry. Replaced with `FloorGuardDecision.ShouldReportNow`, a pure, deterministically-tested latch: report once when the grace window first elapses, then again only after a further full grace window if the breach persists — a bounded fallback cadence instead of an unbounded one.
- **Silent HeartBeat invalidations** (Round 9): the most common outcome of a configured `HeartBeat` callback (an "unhealthy" verdict, triggering replacement) had no telemetry of its own. Added a dedicated `ringbufferplus.heartbeat.invalidations` counter and log message.
- **`acquire.*`/`scale.*` metric-vs-trace tag asymmetry** (Rounds 4, 5, 6): a tag present on a metric but missing from its corresponding trace `Activity` (`success`, `warmup_failed`) was found and fixed on three separate signals across three rounds, each time confirmed by a full-repo search for remaining sibling occurrences.
- **Documentation drift on the Monitor's `active` condition** (Round 11): code comments and guides described the Monitor's silence during full utilization as a narrow edge case (only reachable pinned at `MaxCapacity` with genuine backlog). Empirical reproduction (a temporary test probe, since removed) showed it is also silent during ordinary full utilization with zero waiters — a materially broader condition. Corrected in code comments and in [usage-observability.md](../guides/usage-observability.md) and [usage-elastic-autoscale.md](../guides/usage-elastic-autoscale.md).
- **`FixedCapacity`/floor-guard doc contradictions** (Rounds 11–12): several guides described a fixed-capacity pool as never scaling; the floor guard applies unconditionally in every mode, including fixed. Corrected across [concepts.md](../guides/concepts.md), [usage-fixed-capacity.md](../guides/usage-fixed-capacity.md), and the `Elastic` property's own XML doc.

### A deliberately deferred design question

Round 11 also raised whether the Monitor's `active` condition should be *narrowed* (from `waiting >= idle` to `waiting > 0`) so it only goes silent on genuine backlog, not on ordinary full utilization — a real behavior change to the autoscale algorithm, not a documentation fix. Evaluating this showed the existing decision-quality simulation tool (`AutoScaleAlgorithmComparison.cs`, originally used to validate [ADR003V03](../adr/ADR003V03-median-sample-autoscaling-algorithm.md)) does not model `idle`/`waiting` as separate quantities today, so validating the narrower condition would require extending that tool first, not just running it. Given that real cost against the benefit, the decision was to ship v6.0.0 with the documentation fix only (Option A) and record the algorithm change as an open, evaluated design question for a future round — not as a defect against v6.0.0.

### Test-suite hygiene

A separate, read-only investigation (outside the six-front round format) checked whether the test suite had accumulated dead or redundant tests across the v4 → v5.0 → v6 transitions. It found one genuinely redundant file, `RingBufferManagerTests.cs` (7 tests, fully superseded by `RingBufferContractTests.cs`), which was removed. No actual v4/v5.0/v5.1 residue was found elsewhere in the suite.

### Process failures the audit caught in itself

The audit held itself to the same standard it applied to the code:

- Benchmark numbers written into docs immediately after a commit, before re-running against the round's final code state, went stale twice (Rounds 4→5 and 5→6) before a strict "all code first, one clean rebuild, one measurement, write once" sequencing was adopted from Round 6 onward — with no further staleness incident afterward.
- A fix reported as complete in one round (`SafeIsEnabled`, Round 2) was found never actually wired into its call site by the very next round (Round 3), independently by three fronts — the reason every subsequent round treated a prior round's "confirmed" fix as something to re-verify, not assume.
- A round's own report of its fix's scope (Round 7 claiming a telemetry fix covered both `AcquireAsync` and `SwitchToAsync`, when only the former was touched) was caught by empirical testing in the next round rather than by trusting the prior write-up.

## Final state

- **194/194 tests passing** on `net10.0`, clean build (0 warnings, 0 errors) across all three target frameworks (`net8.0`/`net9.0`/`net10.0`), samples, benchmarks, and the docs generator, verified after every fix throughout the audit.
- **Zero Crítico finding since Round 1.** No new class of behavior bug found since Round 10.
- **3 of 6 fronts formally converged** (estabilidade, resiliência, complexidade); desempenho holds a permanent verification role by design; usabilidade and observabilidade closed on a declining-severity plateau under a stop criterion set in advance.

## Verdict

The `v6` branch is considered release-ready as v6.0.0. See [CHANGELOG.md](../../CHANGELOG.md) for the shipped changes themselves.
